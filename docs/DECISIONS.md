# Decisions

Choices made for this sample, and why. Newest last; a decision that changes is superseded by a new line, not rewritten.

| # | Date | Decision | Why |
|---|---|---|---|
| D1 | 2026-11-20 | The function app is a Container App with `kind: functionapp` (`Microsoft.App/containerApps`), not a `Microsoft.Web/sites` app on a Container Apps environment. | Microsoft names the native model as the recommended one for new workloads ([Functions on Container Apps](https://learn.microsoft.com/azure/container-apps/functions-overview), [samples](https://github.com/Azure/azure-functions-on-container-apps)). |
| D2 | 2026-11-20 | It is declared with azapi (`Microsoft.App/containerApps@2025-07-01`), in a module of its own (`infra/modules/function-app-container-apps`). | `azurerm_container_app` has no `kind` argument in azurerm 4.x; the Azure Verified Module for container apps also uses azapi. |
| D3 | 2026-11-20 | Blob uploads reach the functions through Event Grid: a system topic on the data storage account delivers `BlobCreated` events of the `receipts` container to the `receipts-uploaded` queue, with the topic's own managed identity; a queue-triggered function reads the blob. | No function key to create or rotate, everything in Terraform, and a queue trigger whose scaling rule Container Apps generates. |
| D4 | 2026-11-20 | No keys or connection strings: host storage (`AzureWebJobsStorage__accountName`, `__credential`, `__clientId`) and the data account (`DataStorage__blobServiceUri`, `__queueServiceUri`, `__tableServiceUri`, `__credential`, `__clientId`) use the app's user-assigned identity; both accounts have shared keys disabled. Telemetry to Application Insights with Entra authentication. | Passwordless by default; separate accounts keep the Functions host's own blobs, queues and tables apart from the sample's data. |
| D5 | 2026-11-20 | The container listens on port 8080 (`ASPNETCORE_URLS=http://+:8080` in the Dockerfile; the base image `mcr.microsoft.com/azure-functions/dotnet-isolated:4-dotnet-isolated10.0` listens on 80). Until azd deploys the image, the app runs `mcr.microsoft.com/azure-functions/dotnet8-quickstart-demo:1.0` on port 80. | The project's postdeploy step re-provisions every service still on port 80; with 8080 it runs once, after the first deployment, as for any container app. |
| D6 | 2026-11-20 | Scale from 0 to 10 replicas; Container Apps generates the scale rules from the triggers (HTTP and the queue). | Idle costs nothing; the [overview](https://learn.microsoft.com/azure/container-apps/functions-overview) states the rules are generated and that autoscaling needs ingress enabled. |
| D7 | 2026-11-20 | The scenario: a CSV of fictional receipts (`date,merchant,amount,currency`) uploaded to the `receipts` container is summed per currency by `SummarizeReceipts` (queue trigger), which writes one row per upload to the `ReceiptSummaries` table; `GET /api/summaries` (anonymous, read-only, last 20 rows) lists them. | One pattern end to end (event, queue, function, table, HTTP), with fictional data and nothing sensitive behind the anonymous endpoint. |
| D8 | 2026-11-20 | Each replica of the function app gets 0.5 vCPU and 1 GiB; the app's URL is built from its name and the environment's default domain; the data account's queue endpoint is derived from its blob endpoint. | The sample's work (summing a small CSV) is light and the Consumption profile bills per vCPU-second and GiB-second (assumption, to be measured in [verification](verification.md)); the URL is known at plan time without reading the app back; the shared storage-account module has no queue endpoint output. |
